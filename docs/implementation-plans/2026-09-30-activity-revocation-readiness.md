# Activity Unassign needs a source revocation transaction

This is a deployment draft. The live backend has no Activity revocation columns or RPC. Teacher controls are wired behind an installed-capability check and keep Activity Unassign unavailable on the current backend. Nothing in this slice changes live records or deploys the draft SQL.

The artifact at `artifacts/2026-09-30-activity-revocation.sql` adds independent `revoked_at` and `revoked_by`. Progress status, score, timestamps, snapshots, original `assigned_by`, append-only responses, grades, and mirror metadata remain intact. Revocation is permanent in this version. Reassignment creates a new issued instance; it does not restore the revoked source.

## The server owns the actor and the transaction

`revoke_activity_assignment(p_assignment_id, p_student_id)` requires an authenticated admin, locks the expected student's source row, stamps the actor from `auth.uid()`, and hides every linked Activity mirror in the same transaction. It returns the source/student IDs, original revocation actor/timestamp, this request's actor, whether the source was already revoked, and the count of hidden mirrors. A second admin's retry keeps the first admin's attribution. There is no caller-provided actor parameter. The original teacher attribution is not rewritten.

Existing issuance in `src/lib/assignWork.ts` writes `assigned_by: teacherId` and mirror `created_by: teacherId`. The assignment INSERT policy requires `assigned_by = auth.uid()`. Existing `start_section_attempt` uses the Activity definition's `created_by` because the student is choosing a library attempt, not receiving a new teacher assignment. Do not conflate that author with the actor who later revokes the issued run. Broad existing admin UPDATE permits unrelated source edits; this draft only adds authenticated revocation attribution and prevents all changes to already-revoked assignments.

Atomic source-and-mirror revocation is guaranteed through this RPC. Existing broad admin UPDATE still allows a raw admin edit to set correctly attributed revocation fields without hiding mirrors; that edit is outside the supported operation and must not be used by the client. Existing admin DELETE privileges also remain unchanged. History preservation describes this RPC's behavior, not a guarantee that a privileged administrator can never delete records. Restricting those broader privileges would be a separate migration with a wider compatibility review.

Student source SELECT and UPDATE exclude revoked assignments, including direct API requests. Student response INSERT requires an available source owned by the same account. A response trigger locks the source with `FOR SHARE`, serializing recovery/insert against revocation's `FOR UPDATE`; even a service-role recovery insert cannot append evidence to a revoked source. Visible mirror inserts or unhides require an available source belonging to that mirror's student. Existing history remains stored for admin review. Hiding a mirror alone is still insufficient.

## Wire the UI only after deployment verification

`src/features/activity-centre/api/activityRevocation.ts` probes `activity_revocation_capability()`. Missing RPC, denied access, bad version, or network failure all return unavailable. The helper checks the current authenticated actor, passes the exact source/student IDs, and requires a matching receipt. Teacher Hub and Dossier controls are wired to this capability and remain disabled on the current backend.

The assignment domain types now include optional `revoked_at`/`revoked_by`. The summary reader in `activitiesClient.ts` asks for those fields only when the capability is present; current-backend column lists remain unchanged. Scoped teacher projections retain raw source history but suppress revoked sources and their mirrors from actionable work. After deployment, generated Supabase types must be regenerated rather than hand-edited. `ActivityRunner.tsx` needs an early revocation gate for an admin viewing their own revoked assignment, because admin SELECT intentionally still sees the source; students already get no source row through RLS. That gate is owned by the runner slice, outside this teacher-control work. Keep teacher historical inspection read-only. A mounted student's stale runner will fail source completion and response writes server-side after revocation.

Controls in `HubAssignments.tsx` and `pages/teacher/students/DossierWork.tsx` enable only when the capability probe confirms version 1. They require a confirmation dialog, freeze the issued source and selected student, and refresh both the mirror query and scoped source feed after a confirmed receipt. They do not delete the Classroom mirror or the source row. A missing receipt reports that unassignment could not be confirmed and asks for a refresh before retrying. A confirmed receipt reports success even if the following list refresh fails, with a separate refresh warning. Absent-mirror Activity instances have the same source control. Verify enabled flows using mocked capability/RPC responses until deployment is approved; never use real student records as fixtures.

Before deployment, apply the SQL through the approved Lovable Cloud backend route and verify the deployed catalog/policies. The local harness below uses only synthetic fixtures and is not proof that the live backend has been upgraded. Check existing policy names against the live catalog before installation: PostgreSQL permissive policies combine with OR, so an additional broad student policy would bypass the replacements. Test actual student and admin JWTs on the deployed backend without modifying real student assignments.

## Run the SQL in an isolated local database

On 2026-09-30, `scripts/verification/activity-revocation-concurrency.mjs` passed 32 assertions against isolated PostgreSQL 17 using separate ordinary authenticated connections. Both response/revocation lock orders and concurrent two-admin revocation preserve source history and the first actor. It also applies the preservation wrapper under a nonsuperuser migration role with a separate auth-schema owner, schema USAGE without grant option, and auth.users REFERENCES. An intentionally injected existing-row mutation aborts and rolls back additive DDL. This is local proof, not live JWT acceptance.

The live catalog contains one visible orphan Activity mirror. Installation preserves it. The mirror guard permits unchanged visibility/source/owner with unrelated edits, but denies newly visible orphan rows, source clearing, marker clearing, repointing, and new visible Activity inserts without an available matching source. No orphan repair or deletion is included.

`scripts/verification/activity-revocation-sql.mjs` accepts `--pglite-module` or `PGLITE_MODULE`, points at an externally installed PGlite runtime, creates synthetic auth/admin/student fixtures in memory, and applies the draft SQL. It exercises denied student calls and forged attribution, owner mutation denial, atomic rollback when mirror hiding fails, retained source/response/grade history, idempotence across two admins, blocked mirror resurrection, direct student reads/writes, service-level recovery denial, and new issuance after revocation. No runtime dependency was added to the app.

The client Vitest suite checks capability failure, no mutation against an unsupported backend, expected subject/actor receipt validation, and idempotent attribution. These are contract checks; the executable SQL harness is the database behavior check.

Known boundary: a student with broad Activity library access can choose a new library run. Revoking one issued source is not withdrawal of their entire Activity library entitlement. Audio storage and historical grade reads are not deleted or revoked by this source access operation. Those are separate product decisions.

Live catalog compatibility checked on 2026-09-30: the active uniqueness index uses the draft's existing `(student_id, activity_id)` columns and `assigned`/`in_progress` predicate. The existing source snapshot guard excludes revocation fields and bypasses admins. The installed Classroom student guard blocks visibility, source and owner edits; its update timestamp trigger is installed. The draft retains those guards and adds separate revocation guards. The live schema still has no revocation columns or installed RPC.

The 35 SQL assertions run in one isolated synthetic database. They do not prove concurrent-transaction race behavior, real JWT integration, or live adoption. Row-lock serialization must also be exercised in separate concurrent PostgreSQL sessions before production deployment.
